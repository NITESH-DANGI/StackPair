§1  Overview & Objectives
Frontend Module F-01 implements the complete authentication and onboarding experience for StackPair. It covers every user interaction from first landing on the app through to being in the ACTIVE state with skills configured, platforms connected, and the level computation job triggered. This module is the entry point to the entire product — every other frontend module depends on the state it produces.
1.1  Objectives
Implement Email OTP authentication flow with 60-second countdown and auto-submit
Implement GitHub OAuth and Google OAuth as alternative sign-in paths
Guide users through a 4-step onboarding wizard that maps 1:1 to the backend onboarding_state enum
Enforce the M-01 rule that primary_skill is NEVER collected from or editable by the user
Wire all 22 M-01 backend endpoints to the correct frontend triggers
Produce a JWT-authenticated user session that all product modules can consume via useAuthStore
Handle all error states, validation failures, and edge cases gracefully with clear feedback
1.2  Scope
In Scope: /login, /signup, /verify, /onboarding/profile, /onboarding/skills, /onboarding/platforms, /onboarding/welcome, useAuthStore, authGuard, onboardingGuard, sessionRefresh, all M-01 API integrations.
Out of Scope: Profile editing (F-03), skill level display (F-03), swipe deck (F-04), any M-02 AI verification logic — F-01 only triggers the M-02 job, it does not implement it.
1.3  Success Criteria
A new user can complete signup-to-ACTIVE state in under 3 minutes
OTP delivery confirmed within 10 seconds of request
All 5 onboarding_state transitions trigger the correct backend PATCH/POST and advance correctly
Zero instances of primary_skill being presented as editable in this module
JWT refresh fires on every window focus event and updates sessions.last_seen_at
All 22 M-01 endpoints integrated with correct HTTP methods, headers, and payloads

§3  Authentication Flow Specification
StackPair uses three auth methods: Email OTP, GitHub OAuth, and Google OAuth. There are NO passwords anywhere in the system. Do not build password fields, forgot-password pages, or reset-password pages.

Identical pattern to GitHub OAuth. Button redirects to GET /auth/google. Same backend-driven handshake. Same post-redirect GET /auth/me check.
3.4  Session Management
JWT Storage
F01-AUTH-011
MUST
JWT is stored and managed by the Supabase Auth SDK. Do NOT manually store access_token in localStorage. The SDK handles token persistence and expiry.
F01-AUTH-012
MUST
POST /auth/refresh fires on every window focus event. Wired via TanStack Query global refetchOnWindowFocus config. This updates sessions.last_seen_at (M-01 Fix2).
F01-AUTH-013
MUST
On 401 response from any API call: clear useAuthStore, call Supabase signOut(), redirect to /login.
F01-AUTH-014
MUST
On logout: POST /auth/logout → clear all Zustand stores → Supabase signOut() → redirect /login. The backend sets revoked_at on the session row (M-01 Fix2).
Authorization Header
All authenticated API calls must include: Authorization: Bearer <access_token>. The Supabase SDK provides the current access token via supabase.auth.getSession(). Create an Axios/fetch interceptor that injects this header on every request.
